## Numbered-version branch law

Ordinary Topology Season development does not target `main`.

A numbered branch records a **solid growth phase**, not “whatever we happen to be working on.”

```text
working proof
   ↓ machine proof
   ↓ perceptual / human witness where required
   ↓
topology/v001-...
   ↓
next working body
   ↓
topology/v002-...
   ↓
...
   ↓
release reconciliation
   ↓
main
```

### Seal law

After a numbered branch is sealed and a descendant is cut:

- do not rewrite its history;
- do not keep adding unrelated improvements to it;
- do not force-push it;
- do not “clean it up” to match later understanding;
- fix ordinary bugs forward in the next body;
- use the sealed branch when reproducing what was actually proven then.

```text
SEALED VERSION != FOREVER PERFECT
SEALED VERSION = EXACTLY WHAT WE PROVED THEN
```

### Main law

```text
MAIN = RELEASE FLOOR
MAIN != DAILY DEVELOPMENT AUTHORITY
```

Reconcile the latest season body to `main` only when:

1. all current work we actually want together is present;
2. full proof/package is green;
3. human field witness is acceptable;
4. the body is worth calling an actual release / major build;
5. there is no obvious immediate next topology mutation that should reshape the same carrier first.

The merge to `main` is a **release event**, not housekeeping.

## Release posture

When a numbered body finally integrates the work we want and the next move is no longer obvious:

1. cut a release reconciliation branch from the latest sealed topology branch;
2. reconcile any explicitly wanted side branches;
3. run the whole machine proof;
4. build the real package;
5. perform human field witness;
6. only then merge the release body to `main`;
7. tag/release from that deliberate landing.

Until then:

> **Build forward. Preserve the bodies. Don't babysit main.**
